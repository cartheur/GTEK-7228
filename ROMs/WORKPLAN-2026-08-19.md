## ROM Candidates

### First choice: `ASSIST09`

Why this is the preferred first burn:

- it is the cleanest monitor/bootstrap choice
- it is explicitly described in the sister repo as the best ROM starting point
- it should give the SBC a serial monitor and recovery/debug path

Observed source facts:

- `assist09.bin` size: `2048` bytes
- `ROMBEG EQU $F800`
- source adapted for the SBC's `6850` ACIA

### Second choice: `forth09`

Why this is a follow-on experiment instead of the first burn:

- it is plausible for the target hardware
- it assumes a more specific memory map
- it is larger and more environment-specific than the monitor ROM

Observed source facts:

- `forth09.bin` size: `5711` bytes
- source assembled from `ORG $E000`
- source comments describe an `8 KB` ROM region from `E000-FFFF`

## Working Assumption For 27128 Images

Current image-building assumption:

- EPROM offset `0x0000` maps to CPU address `0xC000`
- EPROM offset `0x3FFF` maps to CPU address `0xFFFF`

That means:

- `ASSIST09` at CPU `0xF800` goes at EPROM offset `0x3800`
- `forth09` at CPU `0xE000` goes at EPROM offset `0x2000`

This is plausible and is supported by the sister repo PCB/BOM notes showing `U2` as `27C128` and the ROM select path labeled `/TOP16K`, but it still remains a placement assumption until proven on the live board.

## Combined Image Observation

It is not safe to assume that `ASSIST09` and `forth09` can simply be packed into one `27128` image.

Why:

- `ASSIST09` is assembled for `0xF800-0xFFFF`
- `forth09` is assembled from `0xE000`
- those two placements overlap in the same top ROM area

Practical consequence:

- an `ASSIST09`-only burn is plausible
- a `forth09`-only burn is plausible
- a combined `ASSIST09 + forth09` image would require relocation or a deliberate custom layout, not a simple merge

See also:

- [docs/27128-image-layout.md](/home/cartheur/ame/aiventure/aiventure-github/cartheur/GTEK-7228/docs/27128-image-layout.md)

## Transport Findings - 2026-08-19

The most important confirmed observations from today's programming tests are:

- raw readback commands work reliably enough to inspect small address ranges
- a one-line Intel HEX file containing only `:10000000FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF00` still produces `*DT ERR @ 0010`
- that means the failure occurs within a single 16-byte Intel HEX record, at the internal advance to the next address after `000F`
- the resulting programmer error is typically `*DT ERR @ 0010`
- the same `*DT ERR @ 0010` behavior was reproduced both with a `27128` inserted and with no device inserted at all

Interpretation:

- the chip itself is not the cause of the present `DT ERR @ 0010` failure
- the unresolved problem is in the `P`-mode Intel HEX transfer path, not basic serial interactivity
- earlier theories that focused only on continued multi-record sessions were too narrow
- current evidence points most strongly to host pacing or end-of-record timing during Intel HEX programming

Additional confirmed clue:

- a previous `*ST ERR @ 0005` on a distinct data record showed that FIFO overflow can occur if the sender outruns the programmer during real programming

Current sender direction:

- the Python transport helper in `scripts/gtek-send-intel-hex.py` is being tuned toward:
  - per-character pacing
  - device-feedback-aware waiting
  - record completion based on idle-without-error rather than requiring a perfect full echo
  - explicit modem-line control so host `DTR` can be driven toward 7228 `CTS`
  - explicit modem-line observation so host `CTS` can be used as a proxy for 7228 `DTR`
- the Tcl app's Intel HEX path was corrected to watch for `*...ERR` or prompt return instead of counting echoed bytes

Tcl cleanup note:

- the Tcl app was returned to the simpler intelligent-send baseline after modem-line gating did not improve the `DT ERR @ 0010` behavior on this setup
- the remaining Tcl-side hypothesis is still pacing, not echo matching

Immediate next test:

- use `scripts/gtek-send-raw.py` or `scripts/gtek-send-intel-hex.py` with:
  - `--drive-dtr high`
  - `--wait-cts high`
  - `--show-modem`
- if the adapter exposes modem lines correctly, that should finally let the host respect the same `CTS`-gated send model hinted at by the original DOS software

## Safety Notes

- Do not burn directly from the small raw `.bin` payloads without placement review.
- Always record full ROM reads using the Tcl terminal recording feature.
- Use `scripts/check-intel-hex-capture.py` to verify readback completeness.
- Treat `ASSIST09` as the safer recovery ROM and `forth09` as the more speculative image.
